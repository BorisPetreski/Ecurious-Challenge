# Privacy controls and Ecurious operating checklist

Ecurious will operate BayReady, as specified by the user. Its exact legal entity, postal address, privacy contact and any responsible data-protection officer have **not** been supplied. This document records implemented controls and the work Ecurious must complete before processing real drivers/camera data in a live rollout. It is not a certification or a claim that code alone makes the service GDPR compliant.

Review date: **24 October 2026**. The [challenge workflow](CHALLENGE-WORKFLOW.md) question 10 addresses plates directly; questions 2, 6–9, 11–15 and 17–19 also introduce personal-data decisions.

## Legal basis for the implementation plan

The GDPR requires purpose limitation, minimisation, limited retention and accountability; each processing purpose needs a lawful basis. Contract necessity and legitimate interests require their own assessment; a blanket consent checkbox does not establish a basis for all camera, account and reservation processing. Rights handling, privacy by design and appropriate security are also required. Relevant articles: 5–6, 12–22, 25 and 32. [Official GDPR text, EUR-Lex](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX%3A32016R0679).

The EDPB's camera guidance calls for purpose-specific necessity/proportionality, consideration of less intrusive methods, clear notices before entering a monitored area, and justified retention. Its discussion of storage beyond 72 hours is **not permission to keep all frames for 72 hours**. Live processing without recording still needs assessment. Use layered signage plus an accessible full notice, and minimise the camera's field of view. [EDPB Guidelines 3/2019, sections 3, 7–9](https://www.edpb.europa.eu/sites/default/files/files/file1/edpb_guidelines_201903_video_devices_en_0.pdf).

## Controls implemented in this change

Open **Map → Profile → Privacy & your data**:

- **Export local profile** opens the native share sheet only after a user action. It can contain the user's own plate/contact data; no automatic upload, log or export file is created by BayReady.
- **Export profile & account bookings** combines local profile, a small current-account identity projection and owner-scoped booking/extension records. If the cloud read fails or returns an unsupported shape, the app does not present a partial result as a complete export. Provider camera records, Auth security logs/backups and other accounts are explicitly excluded.
- **Delete saved profile on this device** has explicit confirmation, serializes with other profile storage operations, deletes the secure profile entry and verifies it is absent. It keeps account/session, bookings and provider data separate.
- **Request account data deletion** records one idempotent request for the current account and displays **Pending Ecurious review—data not deleted**. It neither cancels a reservation nor moves hardware. It is intake, **not fulfilment** of erasure.
- Name, email, phone and plate in the local profile are optional; a supplied value is still validated. Public directory software holds need no plate. Hardware quote/confirmation is gated until the profile includes a plate, with a visible link to add it. The separate chosen email sign-in flow continues to require a valid account email.

Migration ten adds `export_my_bayready_data()`, `get_my_privacy_request()` and `request_my_data_erasure()`, plus private `privacy_erasure_requests`. Public RPCs derive the owner from authenticated `auth.uid()` and take no caller-supplied owner ID. An export explicitly projects the owner's directory/bay/hardware bookings and extension rows; it excludes private fingerprints, camera event keys, dispatch tokens, secrets and images. The hosted check at **2026-10-24T13:20:07.363Z** reported all ten migration checksums matching, no pending migration and eleven application tables, with Auth settings unchanged. Detailed deployment/check evidence belongs in [BUILD-LOG.md](BUILD-LOG.md).

These convenience exports cover their stated scope. A full access request can also concern provider-held data or other justified records. Ecurious needs a monitored rights-request process: authenticate proportionately, find all relevant systems, provide an intelligible response and document any exception. The ordinary response deadline is one month; a necessary extension must be communicated within that month. [European Commission: dealing with requests](https://commission.europa.eu/law/law-topic/data-protection/information-business-and-organisations/dealing-requests-individuals_en), [EDPB: respecting individual rights](https://www.edpb.europa.eu/sme/be-compliant/respect-individuals-rights_en).

## Built-in camera integration and optional model checklist

The primary path uses Ecurious's built-in recognition, already polled by the private worker. It requires no YOLO service or image upload from Expo. Review the actual camera/server retention separately: not saving frames in BayReady does not delete provider-held images or observations. The latest-plate response contains `plateType`, **not a confidence score**; the fictional lab/optional handoff's 0.90 cutoff must not be described as filtering native Ecurious recognition.

The worker requires operator-confirmed disabled device auto-access and queues its own guarded lowering after a fresh private match; it does not install a customer whitelist. Writing `POST /api/v1/locks/:id/whitelist` changes persistent automatic access and can cause lowering; it is not OCR injection or a timed booking. An alternative temporary-plate policy would require durable install/revoke ownership and recovery for uncertain writes, plus an approved way to supply the plaintext plate at activation. It cannot be reconstructed from the stored HMAC. Do not store raw plates for that alternative without a separate necessity/retention decision.

If an external plate model is later added:

1. Identify whether it detects a plate box, reads characters or does both; inspect its output, license, inference dependencies, network calls and any training/telemetry defaults.
2. Configure in-memory processing with no raw frame/plate logging, disk crops, cloud inference or training-data collection by default. If a different mode is needed, assess and disclose that distinct purpose first.
3. Crop the physical field of view and discard irrelevant frames. Avoid faces/audio/person tracking and do not create a cross-site plate history.
4. Enrol camera → assigned lock mapping server-side. Send only the [five event fields](API.md#private-recognition-service-handoff) over authenticated HTTPS; keep the token off phones and out of URLs. A driver cannot submit an authoritative match.
5. Validate fictional/appropriately authorised fixtures for mismatch, low confidence, foreign/temporary formats, stale time, duplicate UUID and a changed vehicle. Record aggregate accuracy/errors; retain raw evidence only under a separately approved necessity/retention process.
6. Give uncertain results an operator-assisted path. Do not bill automatic no-show penalties from a missed camera event or repurpose plate data for retail marketing, employee monitoring or model training.

This is an engineering plan and a source-backed operating checklist. Ecurious must complete the missing organisational/legal measures and validate the actual deployment before making a compliance claim.
